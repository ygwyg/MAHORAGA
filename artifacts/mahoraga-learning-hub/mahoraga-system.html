Architecture

MAHORAGA is an agentic trading harness.

It runs on Cloudflare, uses a Durable Object as the always-consistent brain, stores state in D1 and KV, calls OpenAI-compatible LLMs for research, and executes paper trades through Alpaca.

Plain-English version

MAHORAGA is a disciplined assistant. It watches markets, writes research, checks rules, asks a risk manager for permission, and then sends orders to Alpaca only when the policy allows it.

System map

The major components.

Cloudflare Worker

Public HTTP API and scheduled cron entry point. It handles dashboard requests, agent control, CORS, auth, and routing into the harness.

Durable Object

The single-state coordinator. Durable Objects prevent multiple overlapping brains from racing each other when deciding trades.

D1 database

Stores structured trading records: events, approvals, trades, journals, and risk state.

KV cache

Stores lower-friction cached data such as signals and temporary market context.

Alpaca provider

Wraps account, market data, orders, options, positions, and trade execution calls.

LLM provider

Summarizes catalysts, confidence, risk, and decision context. The current blocker is deployment/model configuration.

Runtime loop

How MAHORAGA decides when to trade.

Cron/API wakes agent

Schedules or dashboard controls trigger the Worker.

Harness loads state

Durable Object reads account, positions, risk limits, signals, and configuration.

Strategy gathers signals

Gatherers collect market data, news, social/catalyst context, and current portfolio facts.

LLM researches candidates

Prompts turn raw signals into a thesis, risk notes, confidence, and trade context.

Rules and policy decide

Entry/exit rules plus risk checks decide whether an order is allowed.

Strategy pattern

The newest upstream update made MAHORAGA easier to extend.

Upstream extracted strategy code out of the monolithic harness into `src/core` and `src/strategy`. That is important because strategy logic can now evolve without turning the whole bot into one risky file.

Core layer

Core code is the platform: environment types, policy broker, execution primitives, and shared contracts. Change this carefully because every strategy depends on it.

Strategy layer

Strategy code is where new trading ideas belong: gatherers, prompts, entry rules, exit rules, and strategy registration. This is where founder learning should focus first.

Extension ladder

Build capability in this order.

Level 1

Observability

Add better decision journals: why the signal mattered, what the LLM said, which rule passed, which risk gate approved it.

Level 2

Risk controls

Improve daily loss limits, max open positions, asset allowlists, options disablement, and manual approval workflows.

Level 3

Signal quality

Add one high-quality signal source or filter. Measure whether it improves paper outcomes before adding another.

Level 4

Backtesting and replay

Create a replay harness that can run a strategy over historical data and compare decisions against future outcomes.

Level 5

Productization

Turn the dashboard into an operator cockpit: thesis cards, approvals, charts, audit trails, alerts, and weekly performance summaries.

Known safety caveat

Options execution should stay disabled until reviewed. The stock path has clearer policy controls; options are complex and can lose money fast even when direction is right.

Best first product improvement

Add a decision-review cockpit before adding new trading logic. Revenue comes from measured edge; measured edge requires high-quality records.
